> 博客侧栏那页友情链接，我加了三年，也放了三年。名字、头像、一句话介绍，摆得整整齐齐，然后就没有然后了——谁上周写了新东西，谁半年没更新，我一个都不知道。最近把它改成了一条会自动往前走的时间线：50 个站点、489 篇文章，谁更新了就自己冒出来。这篇把这套东西是什么、怎么跑的、以及我这边踩过的坑都摊开写一遍。

<!-- more -->

## 一、友链页最大的问题，是它不会动

大多数博客的友链页是一份静态名单。写进主题模板里，或者塞进一个页面，加完就再也不碰。它解决的是「我认识谁」，但回答不了「他们最近在写什么」。

以前想看朋友更新，只有两条路：装个 RSS 阅读器逐个订阅，或者自己写爬虫挨个站点抓。前者要维护一份订阅列表，后者要处理各种页面结构、反爬、站点下线，写起来不难，维护起来没完。

我最后的判断标准很简单：**这件事应该由服务端定时跑，不该由浏览器每次打开页面时算。** 所以做了个独立的小服务，给它一份友链名单，它负责抓、负责去重、负责存，博客只管拿数据渲染。

{% image https://cdn.dusays.com/2026/11/898-1.webp ratio:1918/866 %}

## 二、给一个地址，它自己把整页友链接收下来

最省事的地方在录入。不用一条条填站点名、主页、RSS 地址，直接把 `/friends/` 这类友链页的地址粘进去，它会解析出里面的链接和名字，之后还定期回看有没有新朋友。

不想让它解析也行，手动加单个站点、导入 OPML 都支持。三条路覆盖的情况不一样：页内自动解析适合友链页规整的；OPML 适合本来就在 RSS 阅读器里攒了一份订阅的；手动补适合个别没被认出来的。

{% image https://cdn.dusays.com/2026/11/898-2.webp ratio:1918/866 %}

## 三、没 RSS 也能抓，四层依次兜底

真正麻烦的从来不是「有 Feed 的站点」，而是那些没开 RSS、换了生成器、或者把 Feed 藏得很深的。这套服务按顺序试四层：

1. **Feed**：先找标准 RSS / Atom；
2. **框架指纹**：认出是 Hexo、WordPress 还是别的，按框架惯例去找；
3. **启发式**：从首页链接里猜文章页的规律；
4. **自定义规则**：前三层都不行，允许针对这个站点单独写规则。

关键是最后有个明确反馈：实在抓不到，会告诉你卡在哪一层，而不是静悄悄留个空。这点比「全自动」重要得多——抓不到可以人工补，不知道为什么抓不到就只能干瞪眼。

## 四、按自己的节奏跑，别去打扰已经下线的博客

文章和友链各设各的 cron，互不绑死。友链页一周回看一次就够，文章流可以几小时拉一次。

还有个容易被忽略的细节：**失败站点自动降频**。某个博客连续几次连不上，就把它往后排，不再按原频率反复敲。友链里总有几个站点慢慢就不维护了，服务器关了、域名到期了，如果抓取器还每天准时去撞一次，日志里全是超时，也谈不上对人家客气。

我这边现在是 50 个友链站点、45 个正常抓取，剩下的自动降频，不再按原节奏去撞。

## 五、后台：抓取状态都摊在桌面上

服务端在跑，也得有个地方能看它跑得怎么样。后台是个独立的控制台，登录后第一屏就是概览：50 个友链站点里 45 个正常、5 个异常，收录 489 篇文章、449 篇已生成摘要，近 7 天新增 115 篇，抓取成功率 81%。下面按天铺开近 14 天的收录趋势，旁边是抓取健康的环形图和「需要留意的站点」——连续失败次数最多的几个直接列出来，不用翻日志猜。

{% image https://cdn.dusays.com/2026/11/898-6.webp ratio:1491/833 %}

友链管理页是平时最常来的地方。每个站点一张卡，主页、RSS 地址、文章数、最近成功时间和连续失败次数都写在上面；抓不到的会标出具体原因，比如目标站点拒绝访问、页面由 JavaScript 渲染导致静态抓取拿不到文章、连接超时。前面说的「失败站点自动降频」，在这里就是「已暂停采集 · 暂停于 1 天前」这样一条明明白白的状态，可以点「恢复」重新纳入，也可以进「规则」针对这个站点单独写抓取规则——正好对应第三节的第四层兜底。

{% image https://cdn.dusays.com/2026/11/898-7.webp ratio:1491/833 %}

设置页放的是需要自己决定的几件事：API Key 一键生成或重置，旁边直接给出可复制的 `curl` 示例；AI 摘要的开关、模型服务商和模型名都在这里填，用自己的 Key，Key 只存在自己的账号里；采集频率则把「多久抓一次文章」和「多久回看一次友链页」分开设置，互不绑死。

{% image https://cdn.dusays.com/2026/11/898-8.webp ratio:1491/833 %}

## 六、数据是你的，接口也是开放的

这套东西不要求你把页面嵌进博客，也不要求改主题。一个 GET 请求拿到结构化数据，前端想怎么排都行。

{% image https://cdn.dusays.com/2026/11/898-3.webp ratio:1918/866 %}

取最近 10 篇、按发布时间倒序：

{% raw %}
```bash
curl -H "X-API-Key: your_key" \
  "https://ducircle.dusays.com/v1/all?start=0&end=9&rule=created"
```
{% endraw %}

返回的是干净的 JSON：

{% raw %}
```json
{
  "data": [{
    "title":   "给博客换了个静态生成器",
    "author":  "木子学习笔记",
    "link":    "https://example.com/posts/42/",
    "created": "2026-11-11T08:30:00",
    "summary": "从迁移到部署的完整记录",
    "score":   9.2
  }],
  "total": 326,
  "start": 0,
  "end": 9
}
```
{% endraw %}

`total` 是总数，前端拿它算分页；`summary` 和 `score` 没生成的时候是 `null`，所以渲染逻辑要允许字段缺失，别假设每篇都有摘要。时间字段是 ISO 8601，格式化交给前端。

鉴权头是 `X-API-Key`，也支持 `Authorization: Bearer`。Key 在后台「设置 → API Key」里生成，可以随时重新生成，每个 Key 只对应自己的数据，租户之间互相看不到。

## 七、四个只读接口，字段沿用老习惯

{% image https://cdn.dusays.com/2026/11/898-4.webp ratio:1918/866 %}

开放接口一共 4 个，全是 GET，全部只读：

| 接口 | 作用 | 主要参数 |
| --- | --- | --- |
| `/v1/all` | 文章流 | `start`、`end`、`rule`、`site_id`、`only_summarized` |
| `/v1/friends` | 友链列表 | — |
| `/v1/post` | 某站点的文章 | `site_id`（必填）、`num` |
| `/v1/stats` | 统计概览 | — |

排序 `rule` 支持 `created`（发布时间）、`updated`（更新时间）、`score`（推荐分）三种。想做一个「本周最值得读」的榜单，把 `rule` 换成 `score` 就行，不用另写接口。

出错统一返回 `{"detail": "..."}`，中文说明，不甩堆栈：401 是 Key 缺失或已重置、422 是参数不合法并附具体字段、429 是限流、500 可以到服务状态页看。接口清单由 `app.openapi()` 实时生成，`/openapi.json` 可以直接丢给代码生成器，不会出现「文档写的和实际跑的」对不上。

## 八、落回自己的博客：统计卡、摘要、推荐分

我这边把它接成了一页「友链文章」，放在博客导航里。

{% image https://cdn.dusays.com/2026/11/898-5.webp ratio:1918/866 %}

页面上方四张统计卡——友链站点、正常抓取、收录文章、已生成摘要；下面是文章流，按每页 8 篇铺开，每条带头像、站点名、时间、一句话摘要和推荐分。摘要是大模型写的，推荐分也是它打的，作用是先挑值得读的看。这里要说清楚：**摘要需要填自己的 API Key，费用由服务商直接向你收取**，不开也能用，只是没有摘要和分数。

样式按主题的 CSS 变量写，明暗模式自动跟着切，不额外引外部样式表。摘要固定两行、标题窄屏固定两行，卡片等高，翻页时不会一长一短。

## 九、几个真踩过的坑

**CORS 预检**。浏览器直接调跨域接口，服务端得把博客域名加进白名单，否则预检就被拦下，页面一直卡在「正在连接」。如果不想动服务端配置，就在自己博客里加一层反向代理，变成同源请求。我选的是前者，加完用真实浏览器请求验一遍，别只看 `curl`——`curl` 不发预检。

**主题样式会盖掉自定义样式**。页面挂在主题的 Markdown 容器里，正文的 `p`、`div`、`a` 都带着主题规则。字号被顶掉、多行截断失效、层间距莫名多出 20px，全是特异性不够。解法是把正文区所有选择器加上容器前缀提权，别偷懒写 `> div` 这种宽泛清零规则——它会把子元素自己设的间距一起干掉。

**明文 Key 别放进公开仓库**。前端直接调接口，Key 必然暴露在页面源码里。只读 Key 风险可控，但更稳妥的做法是走一层反代，由服务端注入请求头。这个我还没改，先记着。

**别假设摘要一定有**。`summary` 和 `score` 为 `null` 是常态，前端必须能优雅隐藏。我第一版没做这层判断，列表里出现了一堆空块。

## 十、谁适合用，谁不用

适合：友链加了几十个、想在主站有个「朋友们最近在写什么」页面、又不想维护爬虫的人。也适合本来就有 fcircle 类前端、只缺一个稳定数据源的——字段名沿用老习惯，前端改动很小。

不太适合：只有三五个友链，手动点一遍比接 API 快；或者希望连评论、点赞一起聚合的，这套只管文章流。

## 最后

友链这个东西，本来是博客之间互相留个门牌号。名单是静态的，写法是活的。把它从一张名单换成一条时间线之后，我反而更常点进去看了——不是因为多了什么功能，是因为那里终于有东西在动。

站点和 API 文档都在 [ducircle.dusays.com](https://ducircle.dusays.com/)，文档页的清单直接由 OpenAPI 生成，照着复制那行 `curl` 就能跑通第一步。
